# Localisation (i18n)

Ulla-Bella's Chrome extension ships nine languages. English is the default and the
fallback. This document is the authority for how the language is chosen, where the
copy lives, and what Chrome still controls itself.

Supported locales (Chrome locale codes, also the `_locales` directory names):

| Code | Language | Code | Language |
|---|---|---|---|
| `en` | English | `nl` | Nederlands |
| `sv` | Svenska | `nb` | Norsk bokmål |
| `de` | Deutsch | `da` | Dansk |
| `es` | Español | `fi` | Suomi |
| `it` | Italiano | | |

## 1. Where the copy lives

`extension/_locales/<lang>/messages.json` — **Chrome's own i18n file format**
(`message`, `placeholders`, positional `$1` content). It is the single authored
source of every string, and it is also what Chrome itself reads for the manifest
strings (`name`, `description`, `action.default_title` via `__MSG_*__` and
`default_locale: "en"`).

`extension/src/i18n-messages.js` is **generated** from those files by
`scripts/build-i18n.py` and committed, because the extension has no build step and
every context needs the data synchronously. `extension/test/i18n.test.js` fails if
the generated bundle and the locale files ever disagree, so there is exactly one
place to edit wording.

## 2. Why a resolver instead of `chrome.i18n.getMessage()`

`chrome.i18n.getMessage()` always answers in the **browser UI language**. Chrome
has no API to override it per extension (the `?lang=` URL parameter is a debug
aid, not a setting). A language chosen inside Ulla-Bella's own settings could
therefore never take effect through `chrome.i18n`.

So the extension resolves the language itself, in `src/i18n.js`:

```
manual choice (ub.language) ──┐
                              ├─→ language in effect ─→ bundled messages
"Automatic" → chrome.i18n.getUILanguage() ─┘                (en = fallback)
```

- `resolveLanguage(choice, uiLanguage)` is one pure function: a manual choice
  always wins; `auto` maps the browser's tag (`sv-SE` → `sv`, `no-NO` → `nb`) onto
  a supported locale; anything unsupported or unknown falls back to **`en`**.
- The resolved language is applied once per context (`i18n.setLanguage(...)`) and
  every label is read through `i18n.t(key, params)` / `i18n.tn(key, count)`, so the
  whole UI is consistent — popup, editor panel, marker popovers, first-step modal,
  progress block, save bar, status messages, the toolbar tooltip, and every
  `aria-label` and `title`.
- English is the fallback for a missing translation, and the en file is complete by
  construction (the test suite pins key parity across all nine files), so a label
  is never empty and never shows an internal key.

## 3. The choice, and how it is stored

- Storage key: `ub.language` in `chrome.storage.local`; value is `"auto"` or one of
  the nine codes.
- **Written** by the service worker only (message `setLanguage`), through the same
  single-writer queue (`serializeWrite`) every other setting uses, so it can never
  be lost to a concurrent settings write.
- **Read** directly from `chrome.storage.local` by each context (popup, content
  script, worker). Same key, same rule, so the three surfaces cannot disagree.
- The selector lives in the popup's **Settings**, above *Connections*: `Automatic`
  (naming the language the browser would give) plus the nine languages, each
  written **in its own language**.

## 4. What follows the manual choice, and what follows the browser

| Surface | Follows |
|---|---|
| Popup (all text, incl. error messages) | the choice |
| Editor panel, markers, popovers, modal, progress, save bar, status | the choice |
| Toolbar tooltip (`chrome.action.setTitle`) | the choice |
| Extension name, description, toolbar menu label, `chrome://extensions` | **browser UI language** |
| Web Store listing, permission prompts, "extension updated" bubble | **browser UI language** |
| Annotations, page content, the Ulla-Bella brand | never translated |

The manifest strings are Chrome-driven: Chrome resolves `__MSG_extName__` etc. from
`_locales/<browser language>/messages.json` before any extension code runs, and no
API lets the extension change that per user. The settings note under the language
selector says the same to the user, so the difference is not a surprise.

## 5. Switching languages

- **Popup**: applies immediately (the whole popup re-renders).
- **An open editor tab**: applies immediately, no reload. The content script sees
  `chrome.storage.onChanged` for `ub.language` and re-labels the panel, the
  markers and an open marker popover; an open first-step modal is rebuilt with the
  text the user already typed preserved.
- **Toolbar tooltip**: updated on the next job-status update (or immediately, for
  the popup's own changes, since the worker updates its in-memory language when it
  receives `setLanguage`).
- **Chrome-driven surfaces** (name, description, menu): need an extension reload /
  browser restart, because Chrome localises the manifest itself — and even then
  they follow the browser language, not the choice.

## 6. Copy conventions

- **Keys are stable and descriptive**: `panelSendAll`, `errInviteExpired`,
  `progressSubmitted_other`. A key is never the English text.
- **Placeholders** are `$NAME$` and are declared in the `placeholders` block with a
  positional `content` so the same file also works with `chrome.i18n.getMessage`
  (which takes an array). The test suite pins that every language uses the same
  placeholder set for a key, with the same positions (requirement: *"alla språkfiler
  har samma nycklar och kompatibla platshållare"*).
- **Sentences are never assembled from translated fragments.** Where the old code
  concatenated ("…so " + nouns + " " + verb + " not saved"), the combinations are
  enumerated as whole messages (`saveConflictOne`, `saveConflictDescMany`, …), and
  a translated button name inside a sentence is passed as a placeholder
  (`popupDisconnectNote` with `$CLEAR$`).
- **Plurals** use `_one` / `_other` variants selected by `Intl.PluralRules`, so
  adding a language that also needs `few`/`many` means adding keys, not code.
- **Numbers and relative time** go through `Intl.NumberFormat` and
  `Intl.RelativeTimeFormat` (`i18n.n`, `i18n.ago`): "vor 5 Sekunden", "5 sekunder
  sedan", "just now"/"nu". The elapsed-time counter stays `mm:ss` (locale-neutral).
  No calendar dates are displayed anywhere in the extension, so there is no date
  format to localise.
- **Terminology** (one word per concept, used consistently): annotation →
  sv *anteckning*, de *Anmerkung*, es *anotación*, it *annotazione*,
  nl *aantekening*, nb *merknad*, da *bemærkning*, fi *merkintä*;
  session → sv *session*, de *Sitzung*, es *sesión*, it *sessione*, nl *sessie*,
  nb *økt*, da *session*, fi *istunto*.
- **Not translated**: the brand *Ulla-Bella*, the user's instructions and session
  descriptions, page content, and the `Relay`/`Hermes` product names.
- **Service messages are data, not copy**: an `error.message` from the Relay,
  adapter or Hermes is shown as the reason of a failed annotation (it is the
  agent's own wording), and the extension's own error copy is keyed by error
  *code*. An unknown code shows a translated sentence plus the code, never a
  raw English service string dressed up as UI.

## 7. Adding a language

1. Copy `_locales/en/messages.json` to `_locales/<code>/messages.json` and
   translate every `message` (leave the keys and `placeholders` untouched).
2. Add the code to `SUPPORTED` **and** the endonym to `LANGUAGES` in
   `extension/src/i18n.js`; add it to `LOCALES` in `scripts/build-i18n.py` and to
   the `LOCALES` list in `scripts/package-extension.sh`.
3. `python3 scripts/build-i18n.py` and commit the regenerated
   `src/i18n-messages.js`.
4. Run the tests (section 8). The suite fails on a missing/extra key, a changed
   placeholder, a stale bundle or a dead key.

## 8. Verification

```bash
# unit + i18n suite (Node; run from a native path, not a \\wsl.localhost UNC path)
node --test --test-force-exit extension/test/*.test.js

# bundle up to date?
python3 scripts/build-i18n.py --check

# package + all nine locales present
RELAY_ORIGIN=https://relay.example.com ./scripts/package-extension.sh
```

`extension/test/i18n.test.js` covers: the nine locale files exist and carry
identical key sets; no empty messages and no key-as-text; identical placeholders,
declared for Chrome; complete `_one`/`_other` pairs; the bundled module equals the
locale files; `default_locale` is `en` and every `__MSG_*__` key resolves in every
locale; every key the source references exists and no key is dead; the resolution
rules (automatic, unsupported → English, manual wins, stored tag normalised);
English fallback for a missing translation; plural/number/relative-time output per
language; and the translated toolbar tooltip.

## 9. Known limitations

- The manifest strings (extension name/description/menu) cannot follow the manual
  choice — Chrome owns them (see §4).
- Free-text failure reasons that originate in the Relay/adapter/Hermes are shown
  in the language the service produced (normally English). They are agent output,
  not extension copy.
- Translations were written by the implementing agent, not reviewed by native
  speakers. See the task report for the specific phrases that most need a review.
- The extension's console log lines (`console.log("[Ulla-Bella] …")`) are developer
  diagnostics and stay English on purpose.
